# AI Investment Signals - Prospective Experiment Preregistration v1.0

**Preregistered:** 2026-09-17  
**Status:** prospective protocol, to be frozen before outcome analysis  
**Repository:** `Rickhunter-stack/ai-investment-signals`

## 1. Primary research question

Does the prospectively observed combination of qualitative investment signals, company fundamentals and valuation contain information about subsequent benchmark-relative total returns that is not captured by simpler financial or momentum baselines?

This protocol must be able to produce a negative result. Failure to demonstrate incremental predictive value is a valid outcome.

## 2. Experimental universe

The v1 confirmatory universe is frozen to:

`NVDA, AVGO, QCOM, MU, GOOGL, AMZN, ADI, MDT, ISRG, GH`.

No security may be added to or removed from the v1 confirmatory sample because of subsequent performance. Delistings, acquisitions or other unavoidable corporate events remain observations and must be documented rather than silently removed.

Additional securities may later enter an explicitly separate exploratory universe, but they must not be mixed retrospectively into v1 confirmatory results.

## 3. Observation unit

The primary scored observation is the official frozen weekly ticker snapshot generated by the scheduled pipeline. Daily events are evidence inputs, not independent return observations unless a future protocol version explicitly preregisters an event-level experiment.

Only snapshots created prospectively under the repository's integrity rules qualify for confirmatory v1 analysis.

## 4. Information set and T0

### 4.1 Information cutoff

A weekly snapshot may use only information publicly available before its `as_of` cutoff and captured by the research pipeline without future leakage.

### 4.2 T0 return price convention

To avoid intraday timestamp ambiguity and unrealistic execution assumptions, v1 uses a conservative daily-close convention:

- if the frozen weekly snapshot is created after the relevant US regular-market close and that trading day's adjusted close is already available in `market_pit`, T0 is that trading day's immutable adjusted close;
- otherwise T0 is the next US trading day's immutable adjusted close after the snapshot becomes available;
- no intraday price is substituted retrospectively;
- the same calendar/trading-day rule is applied to the assigned benchmark.

This convention applies to the weekly confirmatory experiment. Daily event timestamps remain preserved for future event-level research but do not change v1 T0.

## 5. Price and return convention

The experimental market-data source is `market_pit`, not the legacy `market` table.

Security and benchmark returns use the same immutable `adjusted_close` convention. Once first stored for a ticker/date, a market observation is not overwritten by later vendor revisions.

For horizon H:

`absolute_return(H) = adjusted_close_H / adjusted_close_T0 - 1`

`excess_return(H) = security_return(H) - benchmark_return(H)`

If the exact target calendar date is not a trading day, use the first common US trading day on or after the target date for both security and benchmark. If a corporate event prevents a valid comparable observation, flag the outcome rather than silently imputing it.

## 6. Horizons

Frozen horizons are:

- M+1 = one calendar month after T0
- M+3 = three calendar months after T0
- M+6 = six calendar months after T0
- M+12 = twelve calendar months after T0

### Primary horizon

**M+6 is the primary confirmatory horizon.**

Rationale fixed prospectively: the framework targets industrial/fundamental signals that may require more than a few weeks to be reflected in fundamentals and valuation, while M+12 materially reduces the number of independent observations available during the early experiment.

M+1, M+3 and M+12 are secondary horizons and must not replace M+6 merely because they produce more favorable results.

## 7. Benchmark rule

Benchmark assignment is frozen prospectively by economic exposure, not selected after observing performance.

### QQQ

Use QQQ for technology / semiconductor / hyperscaler names:

- NVDA
- AVGO
- QCOM
- MU
- GOOGL
- AMZN
- ADI

### SPY

Use SPY for healthcare names:

- MDT
- ISRG
- GH

Both SPY and QQQ remain stored prospectively in `market_pit`.

A secondary sensitivity analysis may report every security against SPY and every security against QQQ, but the mapping above is the confirmatory benchmark and cannot be changed retrospectively.

## 8. Model versions

Historical observations retain the model version that generated them.

`weekly-v1.0` remains immutable. Any material change in fields, transformations, weights or scoring rules requires a new version.

A new model version is evaluated prospectively from its activation date. Retrospective application is allowed only as explicitly labeled exploratory backtesting and must never replace the genuine prospective history.

## 9. Current weekly-v1.0 signal model

The current model combines five dimensions:

1. fundamental strength
2. novelty
3. pricing headroom / degree not already priced
4. valuation
5. execution risk

Execution risk is adverse and therefore must be directionally transformed in the composite score. Current v1 weighting remains the repository's existing equal-weight baseline unless a future version is preregistered before use.

Missing components are not imputed merely to produce a score. An incomplete snapshot remains incomplete and is excluded from score-stratified confirmatory tests that require the missing value, while remaining visible in the historical ledger.

## 10. Primary endpoint

The primary endpoint is **M+6 benchmark-relative total return (excess return)** for eligible frozen weekly observations.

The primary descriptive relationship is whether higher prospectively frozen Signal Scores are associated with higher subsequent M+6 excess returns.

Because repeated weekly observations of the same security overlap in time and are not statistically independent, naive observation-level p-values must not be interpreted as confirmatory evidence.

## 11. Primary analysis

Until sample size supports more advanced inference, report:

- number of eligible observations;
- median M+6 excess return by prespecified Signal Score bucket;
- mean M+6 excess return by bucket;
- hit rate (`excess_return > 0`) by bucket;
- Spearman rank correlation between initial Signal Score and M+6 excess return;
- results by ticker and sector to expose concentration.

Prespecified score buckets:

- 0-39
- 40-59
- 60-79
- 80-100

Empty or very small buckets remain reported as such and must not be merged after seeing results solely to improve significance.

## 12. Baselines and ablation

The central claim concerns incremental value. Therefore the full framework must eventually be compared with simpler alternatives using the same T0 observations and horizons.

Prespecified baselines:

### Baseline A - financial only

Fundamental strength + valuation, using the contemporaneous components available in the frozen weekly snapshot.

### Baseline B - momentum

12-1 month price momentum, calculated using only immutable market observations available at T0. This baseline becomes eligible only after sufficient `market_pit` history exists prospectively; earlier observations are not reconstructed with later-downloaded history for the confirmatory sample.

### Baseline C - valuation

FCF yield when valid and available for the company at T0. Sector limitations must be reported rather than hidden.

The principal incremental question is whether the full Signal Score provides useful discrimination beyond these simpler baselines. No baseline is to be dropped because it outperforms the full model.

## 13. Qualitative interpretation

`FACT`, `WEAK_SIGNAL` and `HYPOTHESIS` remain distinct. LLM-derived judgments such as novelty, importance, confidence, pricing status and execution risk are treated as auditable research judgments, not objective measurements.

Future versions should strengthen scoring anchors and source-quality rules, but historical classifications are not rewritten when those rules improve.

## 14. Stories, theses and criticality

Story relationships, investment theses and AI Infrastructure Criticality are currently research-development layers, not part of the v1 primary confirmatory endpoint unless explicitly incorporated by a later preregistered model version.

Industrial criticality should represent relatively structural characteristics such as substitutability, supplier concentration, qualification time, switching cost and capacity lead time. Dynamic research-signal intensity should remain separate to avoid circularity.

## 15. Missing data

No future data may be used to fill a field that was missing at T0.

Rules:

- missing score component: preserve as missing;
- missing valid T0 market observation: defer to the next valid observation under section 4, otherwise flag unavailable;
- missing horizon price: keep outcome pending/unavailable;
- missing fundamental: do not backfill the historical score with a later filing.

Missingness counts must be reported with results.

## 16. Corporate actions and exceptional events

Adjusted prices are used consistently. Acquisitions, delistings, ticker changes, spin-offs and other events that may make a simple adjusted-price return misleading must be explicitly flagged and reviewed under a documented mechanical rule before inclusion in confirmatory aggregate statistics.

No observation may be excluded simply because its return is inconvenient.

## 17. False positives and false negatives

For descriptive diagnostics, a prespecified high-conviction observation is a complete Signal Score >= 80 and a low-conviction observation is < 40.

- **false positive:** Signal Score >= 80 and M+6 excess return <= 0;
- **false negative:** Signal Score < 40 and M+6 excess return > 0.

These are diagnostic definitions, not proof that the investment thesis caused the return. Middle-score observations are not forced into this binary classification.

## 18. Multiple testing and exploratory analyses

M+6 excess return is the primary outcome. All other horizons, subgroup analyses, thesis analyses, alternative benchmarks, alternative score thresholds, criticality analyses and future dashboard correlations are secondary or exploratory unless a later prospective preregistration explicitly promotes them before their outcomes are known.

Exploratory findings must be labeled exploratory. They may generate a new prospective hypothesis but may not be presented as if they had been preregistered.

## 19. Sample size and statistical restraint

No fixed minimum sample size is claimed to magically establish validity. The project will always report raw N and dependence structure.

Before approximately 100 eligible weekly ticker-observations and meaningful representation across several securities, results should be treated primarily as descriptive. Even beyond that point, overlapping horizons and repeated observations require dependence-aware inference (for example block/bootstrap or clustered methods) before strong statistical claims.

Economic magnitude, consistency, robustness and incremental performance versus baselines matter more than an isolated p-value.

## 20. Success and failure criteria

### Evidence supportive of the framework

Support requires a coherent pattern, not one winning stock. At minimum, the full model should show at M+6:

- monotonic or broadly ordered performance across score buckets;
- positive excess-return tendency in higher-score observations;
- positive rank association between score and future excess return;
- behavior not entirely explained by one ticker or one sector;
- incremental discrimination relative to the prespecified financial-only and momentum/valuation baselines when those baselines become eligible.

These criteria are intentionally not converted into a single arbitrary p-value threshold in v1.

### Evidence against incremental predictive value

The framework will be considered unsupported by the accumulated v1 evidence if, after a sufficiently populated prospective sample, scores show no stable relationship with M+6 excess returns, high-score observations do not outperform lower-score observations in a reasonably consistent way, or the full model provides no useful discrimination beyond the simpler prespecified baselines.

A negative conclusion must be preserved and reported rather than repaired by retrospective reweighting.

## 21. Universe and protocol changes

Any future change to:

- universe;
- primary horizon;
- benchmark mapping;
- T0 convention;
- primary endpoint;
- score construction;
- inclusion/exclusion rules;
- success criteria

requires a new dated protocol/model version before the affected future observations are generated.

The v1 protocol remains in Git history unchanged for auditability.

## 22. Selection-bias limitation

The human daily brief selects five high-value items and therefore contains an editorial selection mechanism. It must not be assumed to represent the complete information environment.

The planned investment scanner should eventually monitor the frozen experimental universe independently of the five-item human brief and may emit zero, one or many material events. Until then, conclusions about event frequency or absence of signals must acknowledge this selection bias.

## 23. Data-source limitations

`yfinance` is a practical collection source, not an institutional point-in-time feed. `market_pit` freezes the first value observed by this project and prevents later overwrites, but adjusted historical data may still contain vendor/corporate-action knowledge unavailable in the original past.

Fundamental point-in-time integrity is not yet fully solved. Confirmatory claims involving fundamentals must therefore wait for the dedicated point-in-time fundamental layer or explicitly acknowledge the limitation.

## 24. Planned implementation sequence after this preregistration

1. point-in-time fundamental ledger;
2. deterministic outcome engine for M+1/M+3/M+6/M+12;
3. baseline and ablation calculations;
4. investment-scanner separation from the five-item personal brief;
5. story classifier v2;
6. thesis layer;
7. structural AI Infrastructure Criticality;
8. divergence detection and richer dashboard views.

This order may change for engineering reasons, but no later implementation may silently alter the confirmatory definitions above.

## 25. Final rule

The project exists to test a hypothesis, not to defend it.

**Frozen historical observations, inconvenient outcomes, failed predictions and negative results are part of the dataset and must remain visible.**

# Amendment v1.1 - Market Integrity Convention

**Amended:** 2026-09-18  
**Effective:** for the first and all subsequent market observations generated after this amendment  
**Reason:** the experimental market ledger contained zero observations when this amendment was adopted. The change therefore precedes any confirmatory market T0/outcome and is not informed by realized experimental returns.

This amendment supersedes the market-data mechanics in sections 4.2, 5, 7, 12 (momentum data source), 16 and 23 where they conflict with the rules below. All other v1.0 provisions remain unchanged.

## A1. Source of truth and append-only representation

The confirmatory market-data source of truth is a Git-tracked, append-only JSON journal under `data/market_pit/`.

Each monthly journal is a **flat JSON array**. Each record represents one prospectively observed `(ticker, session_date)` market observation and is appended in deterministic order by `session_date`, then `ticker`. Existing array prefixes may never be rewritten.

SQLite `market_pit` and the legacy `market` table are caches/derived operational stores only. They must not be the authoritative source for confirmatory outcome computation. A cache may be rebuilt from the JSON journal without changing the journal.

## A2. Frozen fields

Each market record must preserve at minimum:

- ticker;
- session date;
- raw close;
- Yahoo adjusted close as a control field only;
- dividend observed for that session, if any;
- split ratio observed for that session, if any;
- observation timestamp in UTC;
- source/vendor;
- collector/library version;
- material request parameters;
- frozen/integrity metadata required by the repository.

The primary experimental price is **raw close**, not Yahoo adjusted close. Adjusted close is retained only to audit and compare conventions.

## A3. No retrospective vendor repair

First observation wins.

A frozen historical record is not rewritten because the vendor later revises a historical close, adjusted close, dividend or split. In particular, an old dividend or corporate action may not be retrospectively inserted from a later download into an already frozen session.

Vendor corrections discovered later may be documented separately as data-quality annotations, but they do not silently modify the confirmatory ledger.

## A4. Eligible completed sessions

The collector must not freeze the last daily bar returned by a market download. A session is eligible only when the same response already contains at least one more recent daily bar.

This rule is primary because it avoids relying only on wall-clock cutoffs and covers partial sessions, holidays and early closes conservatively.

A market calendar may be used as an additional validation layer, but must not weaken this rule.

The collection lookback must be sufficiently long to tolerate ordinary pipeline interruptions. The initial implementation target is `period=1mo`; because the ledger is prospective, missing historical sessions are not silently reconstructed later if doing so would introduce information unavailable when those sessions should have been observed.

## A5. Coverage frozen from first collection

The market collector must prospectively include:

- the ten confirmatory securities: NVDA, AVGO, QCOM, MU, GOOGL, AMZN, ADI, MDT, ISRG, GH;
- confirmatory benchmarks: QQQ and SPY;
- prespecified sensitivity/sector benchmarks: SMH, IHI and XBI.

QQQ remains the confirmatory benchmark for NVDA, AVGO, QCOM, MU, GOOGL, AMZN and ADI.

SPY remains the confirmatory benchmark for MDT, ISRG and GH.

SMH, IHI and XBI are sensitivity/sector comparators only unless a future dated protocol promotes a different role prospectively.

## A6. T0 convention under v1.1

A weekly snapshot may anchor T0 only to an eligible completed session already present in the immutable JSON market journal.

If the snapshot became available only after that completed session, T0 is the first later eligible completed session observed prospectively for which both the security and its confirmatory benchmark have records.

No intraday price is used. No later vendor history may be used to manufacture an earlier T0.

T0 eligibility is decided and frozen prospectively when the anchor is created.

## A7. Total-return convention

Returns are reconstructed from the frozen raw-close and corporate-action records rather than from later vendor-adjusted history.

Let `P(t)` be frozen raw close and let `parts(T0) = 1`.

For each eligible session `t` in `(T0, H]`, processed chronologically:

1. if a split with ratio `s(t)` occurs, update  
   `parts <- parts * s(t)`;
2. if a cash dividend `d(t)` per share is recorded, reinvest it at that session's frozen raw close:  
   `parts <- parts + parts * d(t) / P(t)`.

Then:

`total_return(H) = parts(H) * P(H) / P(T0) - 1`

Benchmark total return is computed with the identical convention.

`excess_return(H) = security_total_return(H) - benchmark_total_return(H)`

Dividend reinvestment at the session close is an explicit modeling convention, not a claim about executable intraday timing. Its purpose is deterministic reproducibility from the frozen ledger.

The implementation must include unit tests covering at least:

- split only;
- dividend only;
- split and dividend within the same return window.

## A8. Horizon measurement date

M+1, M+3, M+6 and M+12 retain their definitions from v1.0.

If the target calendar date is not represented by a common eligible session for security and benchmark, use the first later common eligible completed session present prospectively in the journal. Missing data remain pending/unavailable rather than being reconstructed from future downloads in violation of the ledger rules.

## A9. Momentum and other price-derived baselines

Any confirmatory price-derived baseline, including 12-1 momentum, must use only market observations that were prospectively frozen in the JSON journal and available at the relevant T0.

No later-downloaded historical series may be used to fill pre-ledger history for confirmatory observations. Exploratory reconstructions must be labeled as such and kept separate.

## A10. Corporate and exceptional events

Splits and ordinary cash dividends are handled mechanically by section A7.

Acquisitions, delistings, ticker changes, spin-offs, special distributions or other events that cannot be represented faithfully by the stated formula must be flagged. Their treatment requires a documented mechanical rule adopted without reference to whether the resulting return is favorable.

No observation is removed merely because its realized outcome is inconvenient.

## A11. Collector provenance

Each frozen record must make the acquisition convention auditable, including the collector/library version and material request parameters. The implementation must pin the `yfinance` version used by the production pipeline rather than silently floating to a new release.

A library/vendor upgrade may occur prospectively, but its activation date/version must remain observable in the ledger.

## A12. Dry-run and production separation

Tests of scheduled-only freeze/outcome logic must use temporary output locations or equivalent non-persistent fixtures.

`workflow_dispatch` must not impersonate the official `schedule` event to create confirmatory freezes. Production confirmatory records are created only by the preregistered scheduled path.

## A13. Integrity condition before first confirmatory market observation

Market Integrity v2 code must implement this amendment before the first confirmatory market observation is accepted.

If that implementation is not ready before an official scheduled run, the schedule should be temporarily disabled rather than create a first cohort using the superseded adjusted-close convention.

This amendment was adopted while the confirmatory market ledger contained zero observations. No historical Signal Score or realized outcome is changed by v1.1.

# Amendment v1.2 - Market Integrity v2 Acceptance Convention

**Amended:** 2026-09-21
**Effective:** before the first confirmatory market collection under the restored schedule  
**Reason:** Market Integrity v2 has been merged while the confirmatory schedule remains paused. No confirmatory market observation has yet been generated under the restored schedule, so these rules are fixed prospectively before outcome generation.

This amendment supplements v1.1. Where implementation details below are more conservative, they govern future confirmatory observations.

## B1. Completed-session rule and early closes

A4 remains primary: a session is eligible only when the same vendor response contains a strictly later daily session. Wall-clock market-close rules never make an otherwise ineligible last bar eligible.

For each weekly snapshot, the scheduled market response freezes a `t0_after_session` boundary for every confirmatory security: the later of the last daily bar returned for that security and its confirmatory benchmark. This boundary is stored inside the immutable weekly snapshot.

T0 is the first prospectively admitted common eligible session STRICTLY AFTER that frozen boundary. No session on or before the boundary may anchor T0, even if it was already present in the market journal. This supersedes the ambiguous timing mechanics in A6 while preserving A6's no-look-ahead purpose. It covers ordinary closes, early closes, holidays and weekends without a wall-clock cutoff.

## B2. Confirmatory collection completeness

A scheduled confirmatory collection is atomic at the run level. Before any market journal write, all 15 frozen series must produce at least one eligible completed session:

NVDA, AVGO, QCOM, MU, GOOGL, AMZN, ADI, MDT, ISRG, GH, QQQ, SPY, SMH, IHI, XBI.

The collector must also reject duplicate session dates, non-positive/non-finite prices and malformed corporate-action fields. A partial run writes no confirmatory market observations.

## B3. Corporate-action consistency

Yahoo/yfinance fields are vendor observations, not unquestioned ground truth. For each eligible row, the project preserves vendor close, adjusted close, dividend, split ratio, repair flag, collector version and material request parameters.

Because Yahoo historical Close and dividend fields may be split-adjusted, the collector reconstructs the A7 raw-price convention using split events present in the same prospectively observed response. Vendor values remain stored separately for audit.

Before schedule activation, automated fixtures must cover at least: no action, cash dividend, 2:1 split, reverse split, split plus dividend, dividend before later split, multiple splits and malformed/non-finite action data.

A vendor inconsistency that makes the mechanical reconstruction ambiguous must fail the confirmatory run or be explicitly flagged unavailable. It must not be silently repaired using later-downloaded history.

## B4. Interruptions and lookback

The confirmatory journal is prospective. After an interruption, sessions that were not observed under the prospective eligibility rule are not backfilled merely because they later appear in a vendor history download.

The one-month request window is a transport/recovery window, not permission to reconstruct missed confirmatory history. On every run, only the newest eligible completed session per ticker may be appended. Older eligible bars returned inside the one-month lookback are context for completion and split reconstruction only and are never backfilled. After an interruption, missed sessions therefore remain absent and visible as missingness.

If the interruption exceeds the configured lookback, the run must record/report the gap; it must not claim continuous point-in-time coverage.

## B5. Run provenance

Each confirmatory scheduled run must expose immutable provenance sufficient to link generated market observations, T0 anchors and outcomes to the execution that created them. At minimum this includes the Git commit SHA and GitHub Actions run ID for confirmatory writes, in addition to each market row's `observed_at`, collector/library version and request parameters.

Manual, push and pull-request runs remain non-confirmatory and must not write the market journal, weekly frozen snapshot or outcomes.

## B6. Append-only acceptance

Repository checks must reject modification, deletion or prefix rewriting of existing frozen arrays in `data/market_pit`, `data/weekly_signals.json`, `data/outcomes_v1.json`, `data/fundamentals_pit` and `data/brief_events`.

New appended market rows must also pass schema/integrity validation before a scheduled commit: frozen=true, ticker in the frozen 15-series market universe, valid ISO dates/timestamps, finite positive raw close, recognized series type, collector provenance and unique `(ticker, session_date)`.

GitHub branch protection/rulesets are an infrastructure control outside the repository. Before schedule activation, `main` should require the relevant integrity checks to pass before merge. The repository cannot itself prove that this external setting is enabled.

## B7. Outcome maturity

An M+1/M+3/M+6/M+12 outcome may use only a frozen market observation already present prospectively in the Git journal. A later vendor download may not manufacture a missing historical horizon price. The first common eligible session on or after the calendar target is used only if that session itself was prospectively admitted to the journal.

Outcome writes remain gated to the official confirmatory schedule.

## B8. Activation gate

The confirmatory schedule may be restored only after all of the following are true:

1. Python sources compile and the full integrity test suite passes.
2. Market-journal append-only and schema validation pass.
3. Tests cover the corporate-action and T0 cases specified above.
4. A manual/push dry run demonstrates zero confirmatory writes.
5. The 15-series completeness rule fails closed.
6. Long-interruption behavior is tested and documented.
7. Run provenance is present in confirmatory records.
8. Branch-protection/ruleset status has been manually verified on GitHub.
9. An independent code review finds no P0/P1 issue affecting prospective integrity.

Restoring the cron is a separate, explicit change after this acceptance gate. Merging this amendment does not itself activate confirmatory collection.
